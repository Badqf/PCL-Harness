# 发布流程（务必遵守）

> 适用于 `tools\release.ps1` 八步一键发版。**先演练，再正式发**；每步都有预期输出，看到 `!!` 先停下判断再继续。

## 0. 本机前提

- 本机只有 **Windows PowerShell 5.1**（没有 pwsh 7）。本文命令统一写成 `powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\release.ps1 …`；在 5.1 会话里、执行策略允许的前提下也可以 `& .\tools\release.ps1 …`。
- 仓库 `F:\PCL2-Source`；发布目录 `F:\PCL2-Release`；GitHub 仓库 `Badqf/PCL-Harness`；tag 形如 `v3.9.4`。
- token 从 `%USERPROFILE%\.git-credentials` 读取（脚本解析 `https://<user>:<token>@github.com`）。
- `C:\Windows\System32\drivers\etc\hosts` 常驻一份第三方屏蔽清单（行尾 `#S302`），把 github.com / api.github.com / codeload.github.com 等 40+ 域名指向 127.0.0.1。浏览器靠 Secure DNS 能绕过，**git 与 .NET 走系统解析会被挡住**。
- 第二个坑：即使 hosts 正常，github.com 的 AAAA（IPv6）不通也会让 git 卡满 300 秒才报超时。所以固定只走 IPv4（见第二节）。
- `release.ps1` 自身必须是 **UTF-8 带 BOM + CRLF**：PowerShell 5.1 按 ANSI 读无 BOM 脚本，会把中文和引号读坏。

## 一、发版前手工改四处

脚本只对第 1 处**强校验**，其余缺了只警告；但发版前应全部改好。

| # | 文件 | 改什么 | 脚本校验 |
| --- | --- | --- | --- |
| 1 | `Plain Craft Launcher 2\Modules\Base\ModBase.vb` | `VersionBaseName` 改成 `"X.Y.Z"`；两处 `VersionCode`（正式版 / 快照版）逐版 +1 | **直接退出**：与 `-Version` 不一致 |
| 2 | `Plain Craft Launcher 2\FormMain.xaml.vb` 的 `ShowUpdateLog` | 在 `If LastVersion < 上一个 VersionCode` 之前插入本版块（`FeatureCount += 1`、`FeatureList.Add(...)`） | Warn：缺了更新日志不显示本版 |
| 3 | `docs\更新记录.md` | 末尾追加 `## §21.30.xx 标题（X.Y.Z）`；体例：背景 / 本次改动 / 影响范围 / 验证 | Warn：正文里没出现版本号 |
| 4 | `README.md`、`README-PCL-Harness.txt` | 「当前版本」与 `FileVersion` 同步 | 不校验（人工） |

只有本次涉及插件 API 变更时，才同步 `PLUGIN-DEV.md` 与 `tools\sdk\README.md`。

## 二、网络：两条通道，脚本自动选

| 维度 | hosts 通道（默认） | resolve 通道（自动降级） |
| --- | --- | --- |
| 前提 | hosts 可写（管理员会话） | 非管理员、或 hosts 被占用/写不进去；也可用 `-ForceResolve` 强制 |
| 是否改 hosts | 临时把 A 记录钉在文件顶部，结束后在 `finally` 里无条件还原 | 完全不碰 hosts |
| 是否需要管理员 | 是 | 否 |
| 实现 | 正常 DNS + `-c http.version=HTTP/1.1` | `git -c http.curloptResolve=<host>:443:<ip>`；REST 与上传用 `curl.exe --resolve` |
| 选 IP | DoH 查到的第一个 IPv4 | 先用 `git ls-remote` / `curl /rate_limit` 逐个探测，取第一个真通的（每个重试 2 次） |
| 失败表现 | 写不进去不抛错：打印 `!! hosts 不可写（…）` 后降级 | 探不到时抛「resolve 通道连不上 github.com…」 |
| 日志特征 | `OK github.com -> <ip>`、`OK hosts 已还原` | `!! 降级为 resolve 通道（不碰 hosts）`、`OK resolve 通道 github.com -> <ip>`、`OK resolve 通道已退出（未改动 hosts）` |

两个通道里 `Host` / `SNI` 都还是 github.com，证书照常校验；resolve 改的是**连接目标 IP**，不是镜像，也不是代理。本机线路会间歇性 `Connection reset`，所以 resolve 通道才要逐个 IP 探测。

## 三、演练（不编译、不推送、不发 Release）

```powershell
cd F:\PCL2-Source

# 1) 强制走 resolve 通道演练：验证非管理员环境下也能发版
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\release.ps1 -Version 3.9.4 -DryRun -ForceResolve

# 2) 按默认通道（hosts）演练
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\release.ps1 -Version 3.9.4 -DryRun
```

预期：先打印 `[预检] Release v3.9.4 是否已存在（只读）` 与 `OK Release v3.9.4 尚不存在，可以继续`（`-DryRun` 也会做这次查询，hosts 通道会临时改写 hosts 再还原；已存在则立即退出，见第六节）；随后 `[1/8]` 打印 `OK 版本 3.9.4，VersionCode=468`；`[2/8]`–`[5/8]` 依次是 `!! DryRun：跳过编译` / `跳过 SDK` / `跳过部署` / `跳过 commit / tag`；`[6/8]` 只做 `git ls-remote`，打印 `OK 连通性正常（DryRun 未推送）：<sha> refs/heads/main`；`[7/8]`、`[8/8]` 跳过。任何一步 `throw` 都会直接停住，先把报错解决掉再进第四节。

## 四、正式发版：八步与预期输出

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\release.ps1 `
  -Version 3.9.4 `
  -Notes @("优化: ……","修复: ……")
```

| 步 | 动作 | 预期输出 / 产物 |
| --- | --- | --- |
| 1 | 预检版本号与工作区 | `OK 版本 3.9.4，VersionCode=468`、`OK 改动文件 N 个`；可能带 `!!` 警告 |
| 2 | 编译（`build.ps1`） | `OK exe 6.1 MB @HH:mm:ss`；失败时日志在 `%TEMP%\release-build-3.9.4.log` |
| 3 | 打包插件 SDK | 生成 `F:\PCL-Harness-Plugin-SDK-3.9.4.zip` 并复制到发布目录，`OK SDK <字节数> B` |
| 4 | 部署 exe | 先强杀正在运行的 `PCL Harness`，再复制；`OK exe <字节数> B sha256=…` |
| 5 | commit / tag | 工作区脏才提交（`feat: release PCL Harness 3.9.4`），无 tag 才创建；`OK commit <sha>` 或 `!! 工作区干净，无新提交`，`OK tag v3.9.4` |
| 6 | push（main + tag 双推） | `OK push main：…`、`OK push v3.9.4：…`、`OK 远端 main = <sha>` |
| 7 | 新建 Release 并上传两个资产 | `OK Release <id> v3.9.4 target=<sha>`，两次 `OK 上传 … B state=uploaded` |
| 8 | 发布后自检 | `OK Release v3.9.4 assets=PCL-Harness.exe, PCL-Harness-Plugin-SDK-3.9.4.zip`、`OK 远端 tag v3.9.4 = <sha>（commit <sha>）`、两条 `OK ghfast 200 …` |

表外还有两处查询 / 拦截检查：**第 0 节 Release 幂等预检**（`OK Release v3.9.4 尚不存在，可以继续`；已存在则立即退出，见第六节）与 **5.5 待上传资产预检**（只在 `-SkipBuild` / `-SkipSdk` 时触发，校验文件存在与新鲜度，`OK exe 新鲜度通过` / `OK SDK 新鲜度通过`，缺失或过期直接退出）。

产物：`F:\PCL2-Release\PCL Harness.exe`、`F:\PCL2-Release\PCL-Harness-Plugin-SDK-3.9.4.zip`（另有中间产物 `F:\PCL-Harness-Plugin-SDK-3.9.4.zip`）。

约定（历史教训）：Release **每版 POST 新建**，禁止 PATCH 复用同一 id；资产只上传到最新一版，不重传给旧 Release，旧 Release 里已有的旧资产脚本不会删除（需要清理请手工 DELETE）；资产名用字面文件名（脚本先把 exe 复制成 `%TEMP%\PCL-Harness.exe` 再传，避免 GitHub 把空格改成点）；正文用 UTF-8 字节 + `charset=utf-8` 提交（脚本已处理，别手拼 JSON）。

### 参数（共 8 个）

| 参数 | 语义 |
| --- | --- |
| `-Version` | 必填；必须与 `ModBase.vb` 的 `VersionBaseName` 完全一致 |
| `-Notes` | 字符串数组，作为 Release 正文（逐行拼接，末尾自动追加一行「· 详见 docs\更新记录.md 与完整更新日志」）；不传则用 `PCL Harness <版本>` |
| `-SkipBuild` | 跳过编译，复用现有 `bin\PCL Harness.exe`；5.5 会检查产物存在且不比源码 / 构建脚本旧 |
| `-SkipSdk` | 跳过 SDK 打包与复制，复用发布目录里已有的同名 zip；5.5 会检查它存在且不比打包素材旧 |
| `-NoPush` | 跳过 push（tag 仍会创建，需要事后手动推）；未同时加 `-NoRelease` / `-DryRun` 会直接 `throw`（避免 Release 与二进制不属于同一提交） |
| `-NoRelease` | 跳过第 0 节 Release 预检与第 7、8 步，只发代码 |
| `-DryRun` | 只做版本号预检、Release 存在性预检与网络连通性，不编译 / 部署 / 提交 / 发 Release / 自检 |
| `-ForceResolve` | 跳过写 hosts，强制走 resolve 通道（演练或排查用） |

### 手动分步（脚本不可用时）

```powershell
cd F:\PCL2-Source
.\build.ps1                                            # → Plain Craft Launcher 2\bin\PCL Harness.exe
.\tools\pack-plugin-sdk.ps1 -Version 3.9.4             # → F:\PCL-Harness-Plugin-SDK-3.9.4.zip
Get-Process -Name 'PCL Harness' -ErrorAction SilentlyContinue | Stop-Process -Force
Copy-Item 'Plain Craft Launcher 2\bin\PCL Harness.exe' 'F:\PCL2-Release\' -Force
Copy-Item 'F:\PCL-Harness-Plugin-SDK-3.9.4.zip' 'F:\PCL2-Release\' -Force
```

然后手工 commit / tag / push；push 仍需按第二节处理网络（或直接 `-SkipBuild -SkipSdk -NoRelease`，让脚本只做第 4–6 步：部署 exe + commit/tag + push）。

## 五、版本号前置条件（脚本实际行为）

- `VersionBaseName` 与 `-Version` 不一致 → `throw` 退出（改好再来）。
- `VersionCode` 找不到（`ModBase.vb 里找不到 VersionCode 声明`）或两处值不同（`…正式版与快照版必须同时改成同一个值…`）也会 `throw`；两处相同才继续，打印 `OK 版本 3.9.4，VersionCode=468`（不校验是否 +1）。
- `FormMain.xaml.vb` 里没有 `If LastVersion < <VersionCode>` → 只 `!!` 警告（用户看不到本版更新日志）。
- `docs\更新记录.md` 里没出现版本号字符串 → 只 `!!` 警告。
- 本地已存在同 tag → 只 `!! 本地已存在 tag vX.Y.Z（将复用）`，不报错。

## 六、Release 已存在怎么处置

第 0 节（在任何编译 / 提交之前）会先做一次**存在性查询**：`GET /repos/Badqf/PCL-Harness/releases/tags/vX.Y.Z`，并打印 `[预检] Release vX.Y.Z 是否已存在（只读）`。

- 返回 **404** → 视为不存在，打印 `OK Release vX.Y.Z 尚不存在，可以继续`，正常往下发。
- 返回 **200**（同 tag 已有 Release）→ 立即 `throw` 退出（退出码非 0），文案：

  ```text
  Release vX.Y.Z 已存在（id=<id>，tag=vX.Y.Z）。
  GitHub 对已存在的 tag 再次 POST /releases 会返回 422 already_exists，本次发版必然在最后一步失败。
  脚本已在预检阶段终止：未编译、未提交、未推送、未创建任何 Release。
  处理方式（二选一）：
    1) 先删除旧 Release（tag 保留）：打开 https://github.com/Badqf/PCL-Harness/releases 删除 vX.Y.Z 后重跑；
    2) 或改用新的版本号：同步修改 ModBase.vb 的 VersionBaseName 与两处 VersionCode，再重跑。
  ```

- 其它错误（401 / 403 / 网络不通）→ 直接 `throw`「查询 Release vX.Y.Z 失败（未编译、未提交、未推送）：…」，不会带着不确定状态继续。
- 预检只在**未加 `-NoRelease`** 时执行；`-DryRun` 也会执行：只查询、不编译、不提交、不发布，但**不是完全无副作用**——走 hosts 通道时仍会临时改写 hosts，并在 `finally` 里还原（还原失败会保留备份并把退出码置 1），只有 resolve 通道完全不碰 hosts。

处置（二选一）：

1. **删旧 Release，保留 tag**：网页打开 https://github.com/Badqf/PCL-Harness/releases 删除该版本，或先 `GET /repos/Badqf/PCL-Harness/releases/tags/vX.Y.Z` 拿到 `id`，再 `DELETE /repos/Badqf/PCL-Harness/releases/<id>`（tag 不删），然后重跑同一命令。
2. **换新版本号**，从第一节重新走一遍。

只想更新代码、不想动 Release：加 `-NoRelease`（跳过预检与第 7、8 步，不创建 Release）。

**兜底**：第 7 步的 `POST /releases` 仍保留 422 `already_exists` 处理（并发或预检被绕过时），文案「创建 Release 失败：… 的 Release 已存在（HTTP 422 already_exists）。请先删除旧 Release 或改用新版本号」。**不要**用 PATCH 复用同一个 Release id（3.7.2–3.7.8 的教训：正文 / 资产被覆盖、`published_at` 停在首版时间）。

## 七、常见失败与处理

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `Release vX.Y.Z 已存在（id=…）` | 第 0 节预检发现同 tag 已有 Release | 按第六节删旧 Release 或换版本号；此时还没有编译、提交、推送 |
| `ModBase.vb 的 VersionBaseName 是 …，要发的版本是 …` | 版本号没改或改错 | 改 `ModBase.vb` 三处再来 |
| 403，响应是 HTML 的 `Forbidden` | 用 `-X Post` 这种小写驼峰调 API，GitHub 当成未知方法 | 脚本已统一转大写；手写 curl 一定要 `-X POST` |
| PowerShell 抛 `NativeCommandError`，但 git / curl 实际成功 | PS 5.1 在 `$ErrorActionPreference='Stop'` 下，把原生命令的 stderr 每一行都当异常 | 脚本的 `Invoke-Native` 局部降为 `Continue`，用 `$LASTEXITCODE` 判断；手写脚本照做 |
| `!! hosts 不可写（…）` | 非管理员，或 hosts 被安全软件占用 | 正常现象，脚本自动降级；想固定走 resolve 就加 `-ForceResolve` |
| `resolve 通道连不上 github.com` | DoH 与备用 IP 全部探测失败，线路不通 | 换管理员会话走 hosts 通道，或检查网络再重试 |
| 第 8 步 `!! ghfast 未通过（code=429/5xx/000）` | ghfast 镜像限流或暂时不可用 | 脚本已按 5 / 15 / 30s 重试 3 次，仍失败只 `!!` 警告、不算发版失败；可稍后手动 HEAD 两个资产。只有 `ghfast 404` 才 `throw`（资产真的不存在） |
| 422 `already_exists`（兜底） | 并发 / 预检被绕过 | 见第六节；正常流程已在第 0 节提前拦下 |

## 八、发布后自检（脚本自动跑，人工再确认）

- `GET /repos/Badqf/PCL-Harness/releases/tags/vX.Y.Z` 的 `tag_name` 等于本版，且 `PCL-Harness.exe`、`PCL-Harness-Plugin-SDK-X.Y.Z.zip` 两个资产按名字逐个校验都在。
- 远端 tag 与本地一致：`git ls-remote origin refs/tags/vX.Y.Z` 指向本地 tag 对象，`vX.Y.Z^{commit}` 等于本地 `HEAD`（`OK 远端 tag vX.Y.Z = <sha>（commit <sha>）`），防止 Release 源码与上传的二进制不是同一份。
- `https://ghfast.top/https://github.com/Badqf/PCL-Harness/releases/download/vX.Y.Z/PCL-Harness.exe` HEAD 返回 200；SDK 资产同样 200。429 / 5xx / 000 重试 3 次后只 `!!` 警告（仅影响镜像分发可达性），404 才 `throw`。
- `PCL Harness.exe` 文件属性里 `FileVersion` = `X.Y.Z.0`。
- Releases 列表里旧版本条目仍在、正文可读。
- 更新记录、`README.md`、`README-PCL-Harness.txt`、SDK 内 README 的版本号一致。
