# ADR-001 3.10.3 的范围：收紧下载上限 + 多镜像回退

- 日期：2026-11-24
- 状态：已实现（3.10.3，构建 480 已发布）
- 参与：顾问（Kimi 外部评审，意见已并入本文件）、执行者（本会话）

## 背景

v10 已开放批量下载、写实例文件、导出整合包、下载源换算。需要决定 3.10.3 先补哪块边界。

## 候选

- A：导出支持真实项目 ID（联网查 CF/Modrinth fingerprint）。
- B：服务器同步的差量下载（清单比对、删除/停用语义）。
- C：收紧边界（下载上限、多 URL 回退）。

## 决定

**做 C，且 C 的内容按执行者核对后修订**：

1. `PluginDownloadOptions.TotalLimitBytes` 增加宿主上限与用户策略，默认 2 GiB 不变。
2. `PluginDownloadRequest` 增加可选多镜像地址，同一 SHA-1、同一文件身份；任一源失败按顺序回退，总重试次数有上限。
3. 不升 `ApiVersionUi`（新增可选，旧插件行为不变）。

B 只写设计与风险清单，不进 3.10.3；A 暂缓。

## 理由

- 顾问给出的排序理由成立：C 是底层能力缺口，B 依赖它；B 的真实风险在清单信任与冲突语义，塞进小版本会同时引入数据损坏与 API 返工。
- 顾问对 C 第一项的前提**不成立**（`ModPlugin.vb:4068` 的上限本来就可由插件设置），核对后把「放开」改成「收紧」——方向不变，动作相反。
- 新增可选字段可以独立回滚，符合「每版能单独回滚」的约束。

## 验收（对应顾问的证伪条件）

- 未修改的 v10 探针回归全绿：`Ok` / `HashMismatch` / `Denied` / `TooLarge` 四种状态与 3.10.2 一致。
- 主源 404、镜像 200 时能回退成功且哈希校验生效；全部失败时 `Failed` 且不留半截文件。
- 插件声明超过宿主上限的 `TotalLimitBytes` 时被夹到上限，`TooLarge` 的消息里写清实际生效值。
## 修订（2026-11-24，第二轮顾问评审后）

C 的实现细节定为：

1. **上限**：`DownloadFiles` 单次调用宿主硬上限 **16 GiB**；用户只能调低；插件请求超过上限时在发起网络请求前**直接报 `TooLarge`**（不静默夹住）。实际接收字节持续计量，超过即终止；磁盘剩余另做前置检查。
2. **多镜像**：保留 `Url` 为首选，新增有序 `AltUrls`；顺序 `Url → AltUrls`；共享同一目标路径与预期 SHA-1，**无 SHA-1 时禁用 `AltUrls`**；每文件总尝试预算 **3 次（含首次）**；网络/超时/408/429/5xx 可在预算内重试，404/410 与确定性 4xx、`HashMismatch` 只换源不重试同一源；`TooLarge`/`Denied`/`Canceled` 立即终止；`AltUrls` 为空时行为与 3.10.2 完全一致。
3. **失败与进度**：全部源失败仍报 `Failed`，消息里拼接逐源诊断；不新增状态。进度用高水位（不回退、不重复累计），仅在启用 `AltUrls` 时生效，且只有校验通过、文件提交完成后才到 100%。

验收（对应顾问证伪条件）：

- 边界：恰好 16 GiB 通过；多 1 字节在联网前失败；伪造小 `Content-Length` 时按实际字节判 `TooLarge`。
- 兼容差分：同一组单 URL 用例与 3.10.2 对比，除「超过新上限」外状态、尝试次数、进度事件一致。
- 镜像：首源 404 次源成功 → `Ok`；首源错误内容次源正确 → `Ok`；全失败 → `Failed` 带逐源诊断；给 5 个源总尝试不超过 3 次。
- 回滚：单独撤销镜像或单独撤销上限，另一项仍正常。

> 口径说明：3.10.2 的插件在超过 16 GiB 时会新增 `TooLarge`，这是本次唯一有意改变的行为，验收以「除新上限外一致」为准。
