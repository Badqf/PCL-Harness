# 插件导入与分发方案（设计稿）

> 状态：设计稿，未实现。目标版本 3.7.0（A+B），C（链接安装）留给插件市场版本。
> 相关代码：`Plain Craft Launcher 2\Modules\ModPlugin.vb`（`Scan` / `LoadOne` / `SetEnabled` / `PluginInfo`）、`Plain Craft Launcher 2\Pages\PagePlugin.xaml.vb`（插件管理卡片）、`tools\sdk\build.ps1`、`tools\pack-plugin-sdk.ps1`。

---

## 1. 问题

现在的分发单位是**文件夹**：用户拿到压缩包 → 解压 → 里面往往多一层 `xxx-main\` → 手动搬进 `PCLHarness\Plugins\` → 有时 `plugin.json` 落在二级目录导致「找不到 DLL / 清单无效」。

由此带来四类麻烦：

1. **导入**：要教用户「解压到哪、别改名、别嵌套」。
2. **更新**：没有覆盖语义，只能删掉旧目录再放新的，`data\` 与设置容易一起丢。
3. **校验**：作者写的 `sha256` 只能事后在日志里发现不匹配，导入时没有统一检查。
4. **来源**：将来做插件市场 / 一键安装时，没有稳定的「包」概念可引用。

## 2. 目标与非目标

**目标**

- 用户操作收敛成「下载一个文件 → 拖进启动器（或点『导入插件』）」。
- 导入前完成校验：清单可解析、id 合法、`sha256` 匹配、`minApiVersion` 兼容、依赖存在。
- 支持**覆盖升级**：替换代码与清单，保留 `data\`、`plugins.settings.json`、启用状态。
- 保持现有文件夹插件 100% 可用、可热重载，不改运行时布局。

**非目标（本版不做）**

- 远程插件市场、评分、自动更新检查。
- 代码签名与信任链（只做「未签名提示」，见 §9）。
- AppDomain / 进程级隔离（属于第二梯队另一项）。

## 3. 总体思路：分发形态与运行时形态分离

```
用户拿到： demo-1.2.0.pclplugin            ← 单个文件（zip 容器）
导入之后： PCLHarness\Plugins\demo\
             plugin.json
             Plugin.dll
             data\                        ← 用户数据，升级时保留
```

运行时仍然扫描 `Plugins\<id>\`，热重载、`sha256` 校验、权限白名单逻辑全部不变。导入只是一层「解包 + 校验 + 原子落盘」。

## 4. 包格式 `.pclplugin`

- **本质是 ZIP**（deflate），只是扩展名用于区分与双击关联；同时接受 `.zip`。
- 内部布局两种都允许：
  - 根目录直接是插件内容（`plugin.json` 在第一层）；
  - 外面套**恰好一层**目录（GitHub「Download ZIP」的常见形态）。
- 定位规则：先看根目录有没有 `plugin.json`；没有就找唯一的第一层子目录里的 `plugin.json`；仍找不到（或找到多个）→ `ERR_NO_MANIFEST` / `ERR_AMBIGUOUS_MANIFEST`。
- 忽略 `__MACOSX\`、`.DS_Store`、`.git\`、`Thumbs.db` 等噪声条目。
- 编码：`plugin.json` 按 UTF-8（可带 BOM）解析；文件名大小写按 Windows 规则比较，但落盘时保留原样。
- 体积限制（防 zip 炸弹）：条目数 ≤ 2000，单文件解压后 ≤ 64 MB，整包解压后 ≤ 256 MB，压缩比 > 200:1 的条目拒绝（`ERR_SUSPICIOUS_ARCHIVE`）。
- 路径安全：拒绝绝对路径、`..\` 穿越、ADS（`:`）、保留设备名（`CON`、`NUL` 等）、符号链接条目（`ERR_UNSAFE_PATH`）。

## 5. 导入管线

```
ImportPackage(path)                       ' 对外入口，返回 ImportResult
  ├─ ReadArchive(path)                    ' 打开 zip、枚举条目、做路径与体积检查
  ├─ LocateManifest(entries)              ' 找 plugin.json（根 / 单层子目录）
  ├─ ParseManifest(json)                  ' 复用现有 plugin.json 解析逻辑
  ├─ ValidateManifest(info)               ' id 规则、版本号、minApiVersion、permissions 合法性
  ├─ VerifyPayload(info, tempDir)         ' sha256（若有）、DLL 是否可加载（仅元数据，不执行）
  ├─ CheckDependencies(info)              ' 依赖的插件是否已安装且版本满足（支持 id@>=1.2）
  ├─ ResolveConflict(info)                ' 已存在：询问 覆盖 / 改名安装 / 取消
  └─ Install(tempDir, info)               ' 原子落盘 + 保留数据 + 刷新列表
```

**id 规则**（与现有扫描一致，导入时强制校验）：`^[a-z0-9][a-z0-9_\-\.]{0,63}$`，不允许中文与空格；不合法 → `ERR_BAD_ID`，提示「plugin.json 的 id 只能用英文小写、数字、`_`、`-`、`.`」。

**原子落盘**（关键，防止导入中途失败留下半个插件）：

1. 解压到 `PCLHarness\Plugins\.tmp\<guid>\`；
2. 校验全部通过后：
   - 新装：`Directory.Move(tmp, Plugins\<id>)`；
   - 覆盖：把旧目录 `Move` 到 `Plugins\.backup\<id>-<时间戳>\`，再把 `tmp` `Move` 到 `Plugins\<id>`；成功后删备份，失败则回滚（把备份移回去）。
3. 覆盖时保留项：`data\`（从旧目录移到新目录）、`plugins.settings.json` 里该 id 的键、`plugins.json` 里的启用状态。
4. 最后 `Scan()` + `RefreshManageRows()`，必要时自动启用（见 §6）。

**错误码表**（`ImportResult.Code`，UI 直接映射文案）：

| 代码 | 含义 | 建议文案 |
| --- | --- | --- |
| `OK` | 成功 | 安装完成 |
| `ERR_NOT_ARCHIVE` | 不是 zip / 已损坏 | 这个文件不是插件安装包 |
| `ERR_NO_MANIFEST` | 找不到 plugin.json | 包里没有 plugin.json，确认下载的是插件包 |
| `ERR_AMBIGUOUS_MANIFEST` | 多个候选清单 | 包里有多份 plugin.json，无法判断用哪个 |
| `ERR_BAD_JSON` | 清单解析失败 | plugin.json 格式有误（可附行号/字段） |
| `ERR_BAD_ID` | id 非法 | id 只能用小写英文、数字与 `_ - .` |
| `ERR_MIN_API` | 需要更高 API | 需要 API v6，当前启动器为 v5 |
| `ERR_SHA256` | DLL 校验不一致 | 插件包里的 DLL 与 sha256 不符，可能下载损坏 |
| `ERR_MISSING_DEP` | 依赖缺失 | 需要先安装 xxx（≥1.2） |
| `ERR_VERSION_CONFLICT` | 依赖版本不满足 | xxx 版本过低 |
| `ERR_UNSAFE_PATH` | 包含非法路径 | 包里有非法路径条目，已拒绝安装 |
| `ERR_SUSPICIOUS_ARCHIVE` | 疑似 zip 炸弹 | 包结构异常，已拒绝安装 |
| `ERR_WRITE_FAILED` | 落盘失败 | 无法写入插件目录（占用/权限） |

## 6. 覆盖升级语义

- 版本比较用现成的 `McUtils.CompareVersion`：
  - 新版本 > 已装 → 「升级」；
  - 相等 → 「重装」（提示会覆盖）；
  - 新版本 < 已装 → 默认「降级」，需要二次确认。
- 覆盖后**启用状态沿用**：原来启用就保持启用，并立即热重载；原来停用保持停用，但列表显示「已更新，尚未启用」。
- 若新包 `minApiVersion` 高于当前 → 拒绝并提示升级启动器。
- 若旧插件正在运行且实现了 `IPclPluginLifecycle.OnUnload`，先 `SetEnabled(False)` 触发卸载，再替换文件（避免文件占用），完成后按需重新启用。
- 失败回滚后，`PluginInfo.Error` 写明「升级失败，已回滚到 <oldVersion>」。

## 7. 单 DLL 导入（方案 B）

- 用户拖入一个 `.dll` 时：用 `ReflectionOnlyLoadFrom`（或 `Assembly.Load(File.ReadAllBytes)` 后只读 `CustomAttributes`，**不执行**代码）读清单元数据：
  ```vb
  <Assembly: AssemblyMetadata("PclPluginId", "demo")>
  <Assembly: AssemblyMetadata("PclPluginName", "示例插件")>
  <Assembly: AssemblyMetadata("PclPluginVersion", "1.2.0")>
  <Assembly: AssemblyMetadata("PclPluginAuthor", "你")>
  ```
  （SDK 的 `build.ps1` 增加 `-PluginMetadata` 开关，自动从 `plugin.json` 生成这些 attribute，作者不用手写。）
- 读取成功 → 在内存里合成 `plugin.json`（`id`/`name`/`version`/`author`/`dll` = 文件名）→ 走同一个安装管线。
- 读不到元数据 → 用文件名当 id、程序集版本当 version，并提示「这是简装插件，无法声明权限与依赖」。
- 限制：单 DLL 形式不能声明 `permissions`（等同「未声明权限」的旧插件，默认放行）、不能声明依赖；UI 上明确标注「简装」。

## 8. UI 与交互

**插件管理卡片（顶部）**

- 工具条：`导入插件`（打开文件对话框，过滤 `*.pclplugin;*.zip;*.dll`）、`打开插件目录`、`重新扫描`。
- 支持把文件**拖进插件页**任意位置（`AllowDrop`，显示高亮边框 + 「松开以安装」）。
- 导入过程显示进度（解压/校验），完成后：
  - 成功：`MyMsgBox` 摘要（名称、版本、来源文件名、「已启用/未启用」）+ 「打开插件目录」按钮；
  - 失败：红字错误码文案 + 「查看日志」。
- 同名冲突：三按钮 `MyMsgBox`——「覆盖升级」/「改名安装」/「取消」；降级时标题写明 `1.2.0 → 1.0.0`。

**列表**

- 卡片右上角增加状态徽标：`可升级`（当导入的版本更高时不再重复提示，仅在冲突时出现）、`简装`（单 DLL 导入）、`未签名`（§9）。
- 每张卡片保留现有「打开文件夹」「事件记录」，新增「卸载」（移入回收站式备份 `Plugins\.trash\`，可恢复）。

**命令（控制台）**

- `import <路径>`：走同一管线，便于自动化测试；`plugins` 输出已装/可升级数量。

## 9. 安全与提示

- 导入前把包里声明的 `permissions` 列出来让用户确认（`net.hosts`、`files.read/write` 摘要），默认聚焦「取消」。
- 未签名包（没有 `signature` 字段，本版不实现签名）显示一次性提示：「插件会以启动器同等权限运行，只安装你信任的来源」。
- DLL 只做**元数据读取**，不做 `LoadFrom` 执行；真正加载仍走现有 `LoadOne`（含 `sha256` 校验与熔断）。
- 导入过程不联网。

## 10. `plugin.json` 可选新增字段

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `homepage` | string | 项目主页，卡片上显示为链接 |
| `license` | string | 许可证标识，仅展示 |
| `signature` | string | 预留（本版不校验） |
| `packageVersion` | integer | 包格式版本，当前 1；用于将来格式演进 |

不写这些字段的旧插件行为完全不变。

## 14. 测试计划

- 正常包（根目录清单）→ 安装成功、可启用。
- 套一层目录的 GitHub ZIP → 自动定位清单。
- 缺 `plugin.json` / 清单损坏 / id 含中文 / `minApiVersion` 过高 / `sha256` 不匹配 → 对应错误码。
- 覆盖升级：`data\` 与设置保留、启用状态沿用、旧版本文件不残留。
- 覆盖失败回滚：把目标目录设为只读模拟写入失败，确认旧版本仍可用。
- zip 炸弹（构造高压缩比文件）与路径穿越（`..\..\evil.dll`）→ 拒绝。
- 单 DLL 导入（带元数据 / 不带元数据）→ 简装标注正确。
- 拖放导入与「取消」路径不会留下临时目录。
