# 2026-11-24-01 3.10.3 优先级 —— 顾问回答

> 顾问：Kimi（用户在其界面调用，原文未改动）。执行者：本会话。

## 推荐

**3.10.3 先做 C：总量可配 + 多 URL 回退，范围到此为止。**
B 作为下一功能版主线，A 暂缓。C 实施期间可以完成 B 的清单、冲突和删除语义设计，但不要把 B 合并进 3.10.3。

## 理由

- **C 是 API 开放后的边界修正**：2 GiB 写死会直接限制大型整合包和未来的服务器同步；单 URL 则把宿主的批量下载能力建立在单一源可用性上。这两项都是底层能力缺口，先补齐能让 B 复用，而不是在 B 中临时打补丁。
- **默认行为可以保持不变**：总量默认仍为 2 GiB；未提供回退 URL 时仍走原路径。已有 v10 插件无需修改，适合快速、独立回滚的小版本。
- **B 不是「差量下载」一个功能点**：真正风险在清单版本与信任、服务端与本地冲突、部分成功后的状态、删除与停用语义，以及失败回滚。把它塞进 3.10.3，容易同时引入数据损坏和 API 返工。
- **A 的价值高但不确定性更高**：联网查询、限流、离线行为、fingerprint 缺失或歧义、项目 ID 匹配错误都会影响导出结果，不宜挡在底层边界修正之前。

## 风险

- **「可配」不能变成插件任意解除资源限制**：建议由宿主或用户策略控制，默认 2 GiB，并设置校验和合理上限；不要允许不受信插件随意声明无限额度。
- **多 URL 必须是同一资源的镜像**：所有 URL 共用同一预期哈希和文件身份，任何源都不能绕过校验；限制重试次数，避免故障时放大请求量。
- **避免隐性破坏 v10**：采用新增可选能力，保留现有单 URL 字段和行为，因此无需升 `ApiVersionUi`。若必须修改原字段语义，就不再属于 C，应升版本并提供迁移说明。新插件还需声明最低宿主版本或做能力检测，防止回滚后被旧宿主误加载。
- C 不应携带持久化迁移或删除逻辑，以保证单独回滚；若过程中发现真实安全漏洞，则按约束拆成独立安全版本。

## 如何证伪

C 的假设是：**小范围补齐边界即可提升可靠性，同时不破坏现有插件。** 可用以下条件验证：

1. 未修改的 v10 插件回归全部通过；默认上限仍为 2 GiB，单 URL 行为与 3.10.2 一致。
2. 用一个真实超过 2 GiB 的任务验证可配上限；用「主源失效、镜像成功」和「全部源失败」验证回退、进度与失败状态，确保哈希不合格时绝不写入。
3. 验证从 3.10.3 回滚到 3.10.2 后，配置不会导致崩溃，新插件会因最低宿主版本或能力检测被明确拒绝。
4. 如果实现开始要求改变现有请求语义、引入清单或删除设计，或者明显超出一个小版本的预算，就说明「C 成本低风险小」被证伪，应停止扩 scope，而不是顺势带入 B。
5. 发布后若镜像回退和大文件场景几乎没有实际使用，而需求主要集中在真实项目 ID 导出，则说明需求排序判断错误，下一版应重新比较 A 与 B，而不是机械执行当前顺序。

## 执行者核对（拿到回答后逐条查代码）

1. **「2 GiB 写死」不成立**：`ModPlugin.vb:4068` 是 `Public Property TotalLimitBytes As Long = 2048L * 1024 * 1024`，插件**可以自己改**；`:4881` 只按这个值判断。所以 C 的第一项不是「让它可配」，而是**给宿主加上限**——现在恰恰相反：插件能声明任意大。
2. **单 URL 成立**：`:4891` `New NetFile({Item.Url}, Target, Checker, False)`，每条请求只带一个地址。
3. **512 MB 是另一条老路径**：`:5391` 的 `HttpDownload` 才有硬上限，与 `DownloadFiles` 无关，不要混。
4. 结论：方向对（先 C），但 C 的内容要改成「**收紧**上限 + 加回退」。这也是执行者不能直接照抄顾问结论的原因。

## 结论（本会话采纳）

- 3.10.3 = 收紧 `TotalLimitBytes`（宿主上限 + 默认不变）+ `PluginDownloadRequest` 可选多镜像回退（同一 SHA-1，重试有上限），不升 `ApiVersionUi`。
- B 单独排下一版，先只写设计与风险清单，不进 3.10.3。
- A 暂缓，等真实需求信号。
