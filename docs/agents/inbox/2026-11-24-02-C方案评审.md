# 2026-11-24-02 C 方案（3.10.3）设计评审

> 顾问：Kimi K3.1 Pro（`moonshotai-cn` / `kimi-k3.1-pro`，通过 workflow 逐次调用）。执行者：本会话。

## 提问（摘要）

定了 3.10.3 只做 C 之后，要定三件事：① 宿主封顶取多少、超过时夹住还是拒绝；② 多镜像字段形态与「同一文件身份」判定、重试预算；③ 全源失败与进度回退的语义。
前提已给代码事实：`TotalLimitBytes` 默认可由插件改；每条请求单 URL；结果状态七种；失败会抛 `AggregateException` 再由宿主逐条判定。

## 顾问回答（要点）

1. **上限**：单次调用 16 GiB 硬上限，不随磁盘浮动；用户只能调低不能调高；插件请求超限时**直接拒绝报 `TooLarge`**，不静默夹住；实际接收字节要持续计量，不能只信 `Content-Length`；磁盘剩余另做前置检查。
2. **多镜像**：保留 `Url` 作首选，新增**有序 `AltUrls`**；顺序 `Url → AltUrls`；所有源共享同一 `Target`、Checker 与预期 SHA-1，**没有预期 SHA-1 不允许启用 `AltUrls`**；每文件总预算 **3 次（含首次）**，优先用未尝试过的源；网络/超时/408/429/5xx 可在预算内重试，404/410 与确定性 4xx、`HashMismatch` 只换源不重试同一源，`TooLarge`/`Denied`/`Canceled` 直接终止；`AltUrls` 为空时完全走 3.10.2 老路径。
3. **失败与进度**：全源耗尽仍报 `Failed`（不新增枚举），诊断里保留每个源的 URL 与异常/状态码；进度用**高水位**，第二个源从 0 重下也不回退、不重复累计，只有校验通过且文件提交完成才到 100%。

## 风险（顾问提出）

- 「旧插件行为完全一致」与「旧插件也受新上限约束」在超过 16 GiB 时冲突，验收口径要写成「除新安全上限外一致」。
- SHA-1 只做完整性，不抗恶意碰撞，不作为 C 的安全承诺。
- 16 GiB 是单次调用上限，不是全局磁盘配额；并发与重传仍会放大消耗。
- 总预算 3 次意味着第 4 个健康镜像不会被尝试，是有意的有界取舍。

## 执行者的取舍

- **采纳**「拒绝而非夹住」：静默夹住会让插件以为下完了却没下完，`TooLarge` 事前报错更好定位。
- **采纳** 16 GiB 与「只能调低」；实现时上限写成常量并存进 `PluginDownloadOptions` 的说明里。
- **采纳** `AltUrls` + 强制 SHA-1：没有哈希就无法定义「同一文件」，允许无哈希回退等于让镜像换文件。
- **采纳** 高水位进度，但**只在启用 `AltUrls` 时**启用；单 URL 路径保持现有进度语义，避免旧插件观感变化。
- **不采纳**「不新增枚举」的字面结论之外的扩展：仍不加 `AllSourcesFailed`，`Failed` 的消息里拼接逐源明细即可。
- 验收按他的四条证伪改写（见 ADR-001 修订）。
