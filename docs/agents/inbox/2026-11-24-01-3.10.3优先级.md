# 2026-11-24-01 3.10.3 的优先级

## 目标

3.10.2 已发（P2 钩子 + 逐文件进度 + 自动更新提示）。下一版先做哪一件：
补 C/D 的剩余（`Host.DownloadFiles` 的进度细节已完，剩服务器同步侧的差量/哈希），
还是先把 API v10 的已知边界收掉（导出只支持 overrides、`DownloadFiles` 单 URL/单文件上限写死 2 GB）？

## 现状与证据

- v10 已开放：`DownloadFiles`、`WriteInstanceFile`、`ExportModpack`（modrinth/curseforge/zip）、`ResolveDownloadUrl`、`PreferOfficialSource`，权限 `instance.write` / `modpack.export`。
- 实测：`.mrpack` 导出 110,437,678 B、`InspectModpack` 回读 `格式=modrinth 名称=Probe modrinth MC=26.3 加载器=fabric`；zip 回读 `格式=archive`（无清单，符合预期）。
- 已知边界：`ExportModpack` 的 `files` 恒为空（不联网匹配 CF/Modrinth 项目 ID）；`DownloadFiles` 每条请求只带一个 URL；总量上限写死 2 GiB。
- issue #1 已关闭：根因是用户机器禁止写 `%TEMP%`，3.10.2 改为明确提示。

## 约束

- 一个版本的改动要能被单独回滚；安全类修复优先单独发（3.9.12 就是这么做的）。
- 插件作者已按 v10 写代码，破坏性改动要走 `ApiVersionUi` 升版 + 迁移说明。

## 候选方案

1. 选项 A：先做「导出支持真实项目 ID」——需要联网查 CF/Modrinth 的 fingerprint，工作量大，且产出依赖网络。
2. 选项 B：先做「服务器同步的差量下载」——`Host.DownloadFiles` 已能给并发/校验，缺的是清单比对与删除/停用。
3. 选项 C：先收边界——把 `TotalLimitBytes` 改成可配、`DownloadFiles` 支持多 URL 回退，成本小、风险低。
