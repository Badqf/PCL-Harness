# 多模型协作约定

这个目录是「执行者（当前会话）」与「顾问模型（例如 Kimi）」之间的文件信箱。
目的：让顾问只出思路、执行者只落地，双方通过文件交接，不靠聊天记录传递状态。

## 角色

| 角色 | 负责 | 不负责 |
| --- | --- | --- |
| 执行者 | 读代码、改代码、构建、实测、发版、取证（日志/截图/命令输出） | 独自拍板有争议的设计取舍 |
| 顾问 | 出选择题：推荐哪个方案、理由、风险、验收标准、怎样证伪 | 直接改仓库文件、跑构建、发版 |

冲突时以**可复现证据**为准（`Log1.txt` 行、命令输出、像素对比），不以谁的措辞更肯定为准。

## 流程

1. 执行者在 `inbox/` 写一份 brief：`YYYY-MM-DD-NN-<主题>.md`，按 `brief-template.md` 的五段式。
2. 顾问在同一目录写回 `<同名>.answer.md`，按四段式：**推荐 / 理由 / 风险 / 如何证伪**。
3. 执行者执行，把结果（命令、日志、diff 摘要）追加到 answer 文件末尾的「执行结果」一节。
4. 结论进 `docs/decisions/ADR-NNN-<主题>.md`，只留决定与理由，不留过程。

## 什么时候值得走一轮

- API 语义或权限模型要改（影响第三方插件，改错代价高）。
- 同一现象有多个候选根因，需要排序。
- 发版策略、兼容性取舍（例如是否为一个 bug 单独发小版本）。
- 自己反复改不动的观感问题（描边、动画这类「像素证据与直觉冲突」的）。

不值得走：改文案、加一行日志、跑一次构建、贴一次测试结果。

## 成本约定

- 每份 brief ≤ 800 字；只贴关键日志片段或 diff 摘要，不整文件粘贴。
- 一轮最多 2 次往返（brief → answer → 至多一次追问）。
- 顾问的回答不直接进代码注释，必须由执行者转述成结论后落地。
